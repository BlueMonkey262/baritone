# v0.2 — multi-version support

Plan for shipping Tenor against several Minecraft versions rather than one. Written 2026-08-02,
against `shulker-restock` at `35881fca` (v0.1.1).

**This reverses a stated non-goal.** `FORK-NOTES.md` lists "supporting more than one Minecraft
version at a time" as explicitly out of scope. That line has to change, and the cost it was
protecting against is real — see §7.

**Standing decision: we do our own version ports.** Tenor stops waiting on upstream branches or PRs
to reach a new Minecraft version. Upstream's ports remain a reference we are free to read and copy
from — both trees are LGPL-3.0 derivatives of the same project, so there is no licensing distinction
to protect — but they stop being a dependency. The point is cadence, not provenance: we ship when
we are ready, not when cabaletta merges.

**Licensing, for the record.** Tenor is and remains an LGPL-3.0 derivative work. Writing our own
ports and our own features does not change that: the tree contains upstream's pathfinder, movement
cost model, mixin layer and command framework. New files we write are ours, but the combined work
stays LGPL. This is not a constraint on anything in this plan; it is a constraint on ever
relicensing, and it is worth writing down once so nobody rediscovers it late.

### Added 2026-08-02: four more targets, in two waves

Eli asked for four older versions. Medium priority, after the three above:

| Wave | Versions | Components? | Expected shape |
|---|---|---|---|
| 1 | 1.21.1, 1.20.1 | 1.21.1 yes, 1.20.1 **no** | 1.21.1 as proven; 1.20.1 needs a shim |
| 2 | 1.21.4, 1.20.4 | 1.21.4 yes, 1.20.4 **no** | same split |

**The 1.20.x pair is not the same job as the 1.21.x pair.** Data components were introduced in
1.20.5, so `upstream/1.20.1` and `upstream/1.20.4` have none. Our tree carries 10 `DataComponents`
references across 5 files — `TOOL`, `FOOD`, `FIREWORKS`, `WEAPON`, `EQUIPPABLE` — and every one needs
a pre-component equivalent (`isEdible`, `DiggerItem`, `ArmorItem`, firework NBT). That is real work
rather than the +74/−74 of mechanical renames the 1.21.11 port cost, and it is the thing most likely
to make these two ports exceed their estimate.

Both 1.21.x targets already reference `DataComponents` upstream, so they are expected to behave like
the 1.21.11 port. Do 1.21.1 before 1.20.1 within wave 1: it validates the pipeline cheaply, and the
1.20.1 shim is easier to scope once the rest of the port is known-good.

When 26.3 releases it becomes `v0.2.x-mc26.3` on the same machinery. Nothing here has to change to
absorb it; that is the point of building a matrix rather than a one-off port.

## 2. The port is small — measured, not estimated

Every number below is from `git diff --stat` against real trees, not an estimate.

| Delta | Files | Lines | Notes |
|---|---|---|---|
| upstream `1.21.11` → `26.1` | 35 | +93 / −97 | Across a Java 21→25 jump; both already mojmap |
| upstream `26.1` → `26.2` | 23 | +135 / −168 | Computed from PR #5076's head |
| Our fork vs upstream `26.1` | 90 | **+16,138 / −152** | Overwhelmingly *new files* |

**The fork is additive, and that is what makes this cheap.** 16,138 insertions against 152 deletions
means we add files rather than editing upstream's. So a version port barely touches us.

**Collision surface, per port:**

- `26.1 → 26.2`: **3 files** — `Settings.java`, `Baritone.java`, `BuilderProcess.java`
- `1.21.11 → 26.1`: **3 files** — `Settings.java`, `InventoryBehavior.java`, `BuilderProcess.java`

And the changes in them are mechanical API renames. **Corrected 2026-08-02** against the real
`upstream/1.21.11` → `upstream/26.1` diff: the shapes actually present are `ClickType` →
`ContainerInput`, `ChunkPos` fields becoming `x()`/`z()` accessors, `new ChunkPos(pos)` →
`ChunkPos.containing(pos)`, and `WaterlilyBlock` → `LilyPadBlock`. The `mc.setScreen` →
`mc.gui.setScreen` and `Tuple`/`getA()`/`getB()` → `Pair`/`first()`/`second()` examples given when
this plan was written **do not occur in that diff** and should not be relied on.

Note also that the raw upstream delta and our adaptation cost are two different measurements, and
this plan originally ran them together: `git diff upstream/1.21.11 upstream/26.1 -- src` is 24 files
and +72/−74, while our own adaptation (`35881fca` vs `tenor/1.21.11`, same feature set either side)
is 25 files and +74/−74.

A port is therefore expected to be: bump `gradle.properties`, fix what the compiler complains about,
resolve three small conflicts. **If the first port disproves that, stop and re-plan** rather than
grinding through four of them.

### Upstream as reference

Upstream has a complete four-loader 26.2 port in
[#5076](https://github.com/cabaletta/baritone/pull/5076) — `minecraft_version=26.2`,
`forge_version=65.0.3`, `neoforge_version=11-beta`, `available_loaders` unchanged. An earlier
concern that 26.2 Forge might not exist upstream was **wrong**; #5075 is a separate, older,
conflicting attempt and can be ignored. [#5082](https://github.com/cabaletta/baritone/pull/5082) is
a draft that mixes the 26.2 bump with a mining-aim behaviour change and older loader versions — also
ignore.

Since we port ourselves, #5076 is a **check, not a source**: do the port, then diff against it to
catch anything missed. **There is no `upstream/26.2` branch** — verified 2026-08-02 — so unlike every
other target in this plan, step 5 has no upstream branch to start from or diff against, only that
pull request's head. Fetch it explicitly before starting, and treat "no reference branch" as part of
that step's cost rather than discovering it mid-port. Its loader version numbers in particular are worth lifting directly, since
those are facts about Forge and NeoForge rather than anything to derive.

## 3. Branch strategy: one per version

Upstream maintains a branch per Minecraft version and does not attempt a unified tree. Match that.
The collision surface is small enough that porting is cheap, and unimined is wired to a single
`minecraft_version` in `gradle.properties`, so a unified tree means version-specific source sets and
a substantially more complex build — buying out a tax we barely pay.

```
tenor/1.21.11   <- upstream/1.21.11 + our feature set
tenor/26.1      <- today's shulker-restock, renamed          [CANONICAL]
tenor/26.2      <- tenor/26.1 + our own 26.1->26.2 port
tenor/26.3      <- tracking only; rebased onto snapshots, never tagged
```

**`tenor/26.1` is canonical.** Fixes land there first, get tested there, then are cherry-picked
outward. Picking one canonical branch matters: without it, "where does a fix go?" gets answered
differently every time and the branches drift.

Note the port direction: `tenor/26.2` derives from `tenor/26.1`, not from upstream's 1.21.11-based
PR, because we already carry the 1.21.11→26.1 changes. Our port is only the 23-file 26.1→26.2 delta.

## 4. Release and tag naming

Eli proposed `v0.2-1.21.11`, `v0.2-26.2`. Readable and unambiguous, with one caveat: those tags do
not sort, because `1.21.11` and `26.2` are not comparable as text — `git tag --sort=version:refname`
and the GitHub releases page will both interleave them oddly.

**Recommendation:** `v0.2.0-mc1.21.11`, `v0.2.0-mc26.1.2`, `v0.2.0-mc26.2`. The `mc` prefix
separates the two version namespaces, and a full semver core keeps the *Tenor* version sortable —
which is the one that actually orders releases.

One GitHub release per supported Minecraft version, so "does this support my version?" is answerable
from the releases page without opening anything. `archives_base_name` should carry it too, so a jar
in a mods folder is self-identifying: `tenor-standalone-fabric-0.2.0-mc26.2.jar`.

## 5. Test instances

The in-game suite is the only coverage reaching processes, and it must run per version — a mixin
that *compiles* against 26.2 can still fail at runtime, which is exactly what this gate catches.

**Exists today:** `1.21.11`, `26.1.2`, `26.2-snapshot-6`, `26.3-snapshot-3`, plus `baritone-testing`
(harness base, 26.1.2 / Fabric 0.19.3) and stale clones `baritone-testing(1)`, `(2)`, `-4`.

**Needed:** one harness base per shipped version, named uniformly.

```
tenor-testing-1.21.11
tenor-testing-26.1.2     (rename of today's baritone-testing)
tenor-testing-26.2
```

Each needs its matching Fabric Loader and Fabric API, and **its own world**. Worlds are the part that
bites: a save written by 26.2 will not open in 1.21.11 and the region format is not backward
compatible. Each instance generates its own world; they cannot be copied between versions.

**Runner changes** to `scripts/testing/parallel_run.py`:

- `--instance <name>` / `--mc-version` to select the base, defaulting to current behaviour
- `--all-versions` to run each configured version in turn, merging reports with a version column
- `diff_baseline.py` gains per-version baselines, `scripts/testing/baseline-<mcversion>.json`. One
  shared baseline is meaningless — tick counts legitimately differ between versions.

**Scenario portability is lower risk than first assumed.** Staging goes through vanilla commands, and
Eli reports command syntax is unchanged since 1.21.11. Treat the first full 1.21.11 run as the
confirmation rather than budgeting for a rewrite — it is a cheap measurement either way.

Cleanup while here: delete the stale `baritone-testing(1)`, `(2)`, `-4` clones, several hundred MB,
flagged in the old handoff and still there.

## 6. CI

Today: `:test` plus a four-loader compile on one version. Becomes a matrix of version × loader —
3 × 4 = 12 compile jobs. Well within GitHub Actions' matrix support. `:test` runs once per version,
since the unit tests are Minecraft-free but the tree differs.

## 7. The ongoing tax

Weigh this before starting; it does not end when v0.2 ships.

- **Every fix is now three ports.** A one-line `RestockProcess` change becomes three cherry-picks and
  three CI runs. Most will be clean given the collision surface, but "most" is not "all".
- **Every release is three releases.** Three tags, three sets of jars, three sets of notes.
- **The in-game gate multiplies.** One curated run is ~205s; three versions is ~10 minutes plus
  per-version flakiness to triage. `parallel_run.py -n 3` already saturates the machine, so versions
  run in sequence.
- **We now own the ports.** Decoupling from upstream's cadence means no waiting — and no free ride.
  When 26.3 releases, the port is ours to do.

Mitigation is the canonical-branch discipline in §3, not heroics.

## 8. Sequencing

Each step gates the next. Stop and re-plan if a gate fails.

| # | Step | Gate to exit |
|---|---|---|
| 1 | Rename `shulker-restock` → `tenor/26.1`; update the FORK-NOTES non-goal | Branch renamed; notes state multi-version is now a goal, and why |
| 2 | Port to **1.21.11** ourselves — the cheap probe | `:test` green, four loaders compile. If the 3-file estimate is wrong, find out here for the price of one port |
| 3 | `tenor-testing-1.21.11` + world; teach `parallel_run.py --instance` | Curated suite runs on 1.21.11 and produces a report |
| 4 | Triage that run; fix any scenario portability | 33/33 on 1.21.11; per-version baseline recorded |
| 5 | Port **26.1 → 26.2** ourselves; diff against #5076 as a check | `:test` green, four loaders compile, nothing #5076 caught that we missed |
| 6 | `tenor-testing-26.2` + world + suite | 33/33 on 26.2 |
| 7 | CI matrix, version × loader | All 12 combinations compile on every push |
| 8 | Tag and release all three | Three releases, notes naming the loaders each version got |
| 9 | `tenor/26.3` tracking branch | Rebases onto snapshots; explicitly untagged and unsupported |

**Step 2 is the decision point.** It is cheap and it tests the central assumption of the whole plan.
